# ADR-004: An Encoder Classifier for Bounded Decisions (System 1)

**Date:** 2026-10
**Status:** Accepted
**Deciders:** raisga core team

## Context

Several p4n4 flows need a small decision from a closed menu: which team should see an
alert, which pump an operator's message is about, whether a request needs the LLM at
all. Until now they asked Ollama for free-form JSON. That is slow on a Pi, the reply
doesn't always parse, and a parse failure in `incident-escalation` set
`notify_team: false`, so the critical alert was dropped.

[laya](https://huggingface.co/convaiinnovations/laya) is an encoder (mmBERT-base for its
`multilingual` checkpoint) that answers *typed questions*. Given a state and a question
with a closed set of options, it returns one option with probabilities and a confidence
in one forward pass, 0.1–0.3 s on two x86 cores. It has no decoder, so it can't write
text or answer outside the options.

The spike ([system1.md](../system1.md) §4) found it fits a Pi-class budget (about 1 GiB
behind a wrapper), and routes well when the menu is closed, the wording is right and the
state holds only evidence. It also found:

- **It is not a zero-shot decision engine.** Rewording one question moved the score
  from 2/8 to 7/8. A placeholder device name in the state sent unrelated alerts to
  `connectivity` with confidence up to 0.90. On p4n4's generic 62-example evaluation
  file, `incident-triage` was confidently wrong on 1 in 7 alerts at the spike's 0.5
  threshold.
- **Yes/no gates and severity scores are unusable** (`noul` 6/14, severity exact on 3/8).
- **Stock `laya-serve` fails silently.** It truncates long states, options and
  instructions and still answers, serves without auth when no key is set, follows the
  Hub's default branch, and loads extra checkpoints on demand. Newer releases add
  per-request budgets, languages and a batch route.

## Decision

1. **System 1 is an opt-in `system1` service in the ai stack**, behind its own Compose
   profile, running laya on the CPU. It is advisory. *Rules decide, System 1 routes,
   System 2 (Ollama, Letta) explains.* Severity, safety, actuation and thresholds stay
   in rules, and every consumer works the same when System 1 is down, slow, unauthorised
   or abstaining.
2. **p4n4 serves laya through its own wrapper** (`system1_app.py`), never stock
   `laya-serve`. The wrapper:
   - pins the model by commit and by the sha256 of every file, built into the image;
   - serves one checkpoint (`multilingual`, or `english`), offline from a read-only
     volume;
   - refuses to start without a 32+ character key;
   - turns every budget laya would truncate into a 422;
   - bounds work per request (8 questions, 4,000 characters, 64 KiB counted as it
     arrives);
   - serves three routes only, and only the `state`, `questions` and `model` fields.
3. **Only `choice` questions, in versioned server-side question sets**
   (`config/system1/questions/<name>.json`). Each set carries per-question thresholds
   that set an `abstain` flag, and an evaluation file with gates (coverage, answered
   accuracy, confident-wrong rate). A set whose gates fail doesn't ship: CI runs every
   shipped set, and `p4n4 ai system1 eval` exits 5 on a project's own copy.
4. **The state is evidence only**: canonical fields in a fixed order, never a raw
   payload, never names or IDs that act as priors. For `incident-triage` that is the
   alert's first line.
5. **Every decision is logged** on `system1/decisions/<set>`, answered or abstained, used
   or not, with the set version and model revision. The state is logged as a hash.
6. **Pin everything**: the base image digest, a `--require-hashes` lock per architecture,
   the laya version, the model commit and file hashes, and the set version. Any change to
   them bumps the set's version and reruns its gates.

## Consequences

- `incident-escalation` v2 escalates every critical alert. A team comes from a rule, or
  from System 1 marked as suggested, and the on-call recipient is always notified. The
  LLM summary follows on its own topic and never delays the escalation.
- The shipped `incident-triage` threshold is 0.9. At that threshold System 1 suggests a
  cause for about a quarter of the alerts no rule routes, and is almost never wrong. A
  site raises that coverage with its own examples (`eval --fit-thresholds`), not by
  lowering the threshold by intuition.
- The image is 1.7 GB, and the service needs 2 GiB and 1–2 CPUs. It is not recommended on
  a Raspberry Pi 4, and its Pi 5 latency is still to be measured.
- The wrapper relies on laya internals (`_check_question`, `_to_internal`,
  `render_options`, the temperature table). The regression suite is the contract for
  them, and every laya bump needs a read diff, the suite and the evaluations. 0.3.17 and
  0.4.6 gave identical probabilities on all 62 evaluation requests.
- One key serves every caller on `p4n4-net`, n8n and Node-RED's `p4n4-system1` subflow.
  `p4n4 secret rotate` rotates it in both layers and updates n8n's credential.

## Alternatives considered

- **An LLM with JSON output (status quo).** Slow on a Pi, open-ended, and its parse
  failures dropped alerts. It stays for explanations, as System 2.
- **laya's `score` and `noul` types** for severity and gates: measured unusable (above).
- **Stock `laya-serve`**: silent truncation, optional auth, unpinned weights and unbounded
  work.
- **Passing the key to n8n as an environment variable**: needs `$env` in expressions,
  which exposes every variable of the n8n container to every workflow. n8n's Header Auth
  credential, which it encrypts on import, is used instead.
- **Fine-tuning first**: deferred to S4, only if the evaluations show the base checkpoint
  is the limit.
