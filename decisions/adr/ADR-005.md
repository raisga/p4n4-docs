# ADR-005: Edge Inference Joins the AI Stack; p4n4-edge Becomes p4n4-extras

**Date:** 2026-10
**Status:** Accepted
**Deciders:** raisga core team
**Supersedes:** the `edge` layer of [ADR-002](ADR-002.md) and [ADR-003](ADR-003.md)'s layer order

## Context

p4n4 ran three stacks on `p4n4-net`: p4n4-iot (MING), p4n4-ai (GenAI) and p4n4-edge, whose
only service was the inference runner (`ei-runner`: an Edge Impulse `.eim`, an ONNX model,
or mock results). Edge inference is part of p4n4's core value next to local GenAI, and
the runner was already like an AI stack service: one container in a Compose profile of its
own name, attached to `p4n4-net`, reading MQTT and writing InfluxDB's `ai_events`. A stack
of its own cost a repository, a layer in `p4n4_lib`, the CLI, the API, the emulator and the
docs, and a third `.env` to keep in step, for one optional service.

There was also no home for services that are useful but not core (a reverse proxy, metrics,
a vector database, video), short of adding them to a core stack.

## Decision

1. **The runner moves into p4n4-ai** as its `ei-runner` service and profile, off by default
   like Letta, n8n and System 1. `runner/`, `edge-impulse/models/` and `onnx/models/` move
   with it. Its container name (`p4n4-ei-runner`), port (8080 on `127.0.0.1`), volume key
   (`ei-runner-data`), MQTT topics and variables don't change. `p4n4 init --layer all`
   enables it, as it ran the edge layer before; `--ei-runner` enables it otherwise.
2. **p4n4-edge is renamed p4n4-extras** (`stacks/extras`): optional services, none enabled
   by default, none depended on by the core. `extras` is a layer (`Layer.optional`), left
   out of `--layer all`. Each extra is a directory of its own (compose file, `.env.example`,
   config), which the layer's `docker-compose.yml` pulls in with `include:`, so all extras
   run as one Compose project with one `.env`, each in a profile of its own name. It ships
   the skeleton extra (`_template/`), no extras; the community catalog of the
   [AI harness design](../ai-harness.md#5-extras-community-stacks) builds on it.
3. **`edge` stays a legacy layer** (`p4n4_lib.layers.LEGACY_LAYERS`): projects that have it
   keep running, ordered after ai, with a reminder. `p4n4 migrate edge` moves it into ai
   (the runner, models, `.env` values, and its service spliced into the ai compose file),
   or, for an edge layer running other services (a template's own), renames it to extras
   with its Compose project name, so its volumes stay.
4. **The network stays `p4n4-net`**, created by p4n4-iot. The stacks stay separate Compose
   projects (ADR-002): the iot stack defines the network the others declare external, so
   they can't merge into one Compose file.

## Consequences

- The core is two stacks. A project's ai layer runs edge inference alone with
  `COMPOSE_PROFILES=ei-runner`, so a sensor-side Raspberry Pi needs no LLM.
- `p4n4 up` (and `p4n4-emu up`) skip a layer with no service enabled, since Compose fails
  on it ("no service selected"); an extras layer starts that way.
- Breaking for existing projects only in what Compose names after the project: the runner's
  volume becomes `<project>-ai_ei-runner-data` and its image `<project>-ai-ei-runner`. The
  runner keeps nothing in that volume, and the image is rebuilt. `edge.pre-migrate/` keeps
  what the migration replaced.
- `p4n4-lib` 0.4.0 (layers, `migrate`, `layout.runner_layer`, `compose.enabled_services`)
  must be published before the CLI, p4n4-api and p4n4-emu that need it, and the p4n4-ai and
  p4n4-extras changes pushed before `p4n4 init` clones them.
- p4n4-api and p4n4-dashboard find the runner with `layout.runner_layer`: the ai layer with
  the `ei-runner` profile, or a legacy edge layer. The dashboard's Edge tab and
  `/api/v1/edge/metrics` keep their names: they describe the edge *device*.
- `P4N4_API_EDGE_RUNNER_URL`, `EI_RUNNER_BIND` and the other runner variables keep their
  names.
